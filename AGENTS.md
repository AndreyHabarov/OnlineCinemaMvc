# Работа с OnlineCinema

## Проект и цель

- ASP.NET Core MVC / .NET 8, Identity, EF Core 8, PostgreSQL, Razor и JavaScript.
- Довести существующее приложение до демонстрации для портфолио. Покупка билетов демонстрационная, без списания денег; выдаёт билеты и сохраняет их в личном кабинете.
- Пользовательские тексты, описания и инструкции писать на русском.
- Очередь задач и выполненные блоки находятся в локальном `backlog.md`. Если файл отсутствует в новом checkout, уточнить задачу из запроса пользователя; не считать его отсутствие ошибкой.
- Демонстрация разворачивается через Docker Compose: web и PostgreSQL в отдельных контейнерах, initialize автоматически применяет миграции и повторяемое сидирование. Постеры локальные; фоновый процесс поддерживает будущие сеансы. Локальная разработка с отдельным запуском сайта также поддерживается.

## Границы изменений

- Следовать актуальному запросу пользователя. Для анализа без изменений не редактировать файлы и не создавать коммиты.
- Пока не менять README и описание репозитория GitHub без отдельного указания пользователя.
- Не коммитить `backlog.md`, `.env`, локальные подключения, секреты, дампы, файлы `backups/` и данные PostgreSQL. Не включать их в Docker-образ.
- Перед работой проверить `git status` и diff. Сохранять чужие незавершённые правки; добавлять в коммит конкретные проверенные файлы.
- После завершённого и проверенного блока изменений делать отдельный коммит и push в текущую согласованную ветку. Не пушить непроверенный блок, не переписывать историю Git. Новые ветки при необходимости именовать с префиксом `codex/`.
- Локальный бэклог обновлять только после подтверждения результата; отмечать отдельно неудавшийся push или неполную проверку.

## Запуск и команды

Команды выполняются из корня проекта.

Для готовой демонстрации (PowerShell 5.1 или 7):

```powershell
./scripts/Start-Demo.ps1
```

Для локальной разработки:

```powershell
./scripts/Initialize-Local.ps1
./scripts/Update-DemoCatalog.ps1
./scripts/Update-DemoSeats.ps1
./scripts/Update-DemoSchedule.ps1
dotnet run --project OnlineCinema.Mvc --launch-profile http
```

- Сайт Docker: `http://localhost:8080`; профиль локальной разработки: `http://localhost:5175`. Контейнерная БД: `127.0.0.1:5434`, база `cinemadb`, пользователь `cinema`. Проверять фактические настройки Compose; пароль не выводить в сообщения или логи.
- Подключение Development хранится в игнорируемом `OnlineCinema.Mvc/appsettings.Development.local.json`; `ConnectionStrings__Default` имеет приоритет.
- Инструкции: `docs/quick-start.md`, `docs/docker.md`, `docs/testing.md`, `docs/local-development.md`, `docs/demo-catalog.md`, `docs/demo-schedule.md`, `docs/ticket-purchases.md`, `docs/admin-catalog.md`, `docs/project-files.md`.

## Проверки

Общая регрессия приложения: `./scripts/Test-All.ps1` (собственная временная БД).
Чистое контейнерное развёртывание: `Test-ContainerMigrations.ps1`,
`Test-ContainerDemo.ps1 -CheckScheduleRefresh`, `Test-ProductionMode.ps1`
в папке scripts. Эти runner создают и удаляют только свои временные
Compose-проекты; рабочие БД и volumes не затрагиваются.

```powershell
dotnet build OnlineCinemaMvc.sln --no-restore
dotnet ef migrations has-pending-model-changes --project OnlineCinema.Domain --startup-project OnlineCinema.Mvc -- --environment Development
./scripts/Test-Authentication.ps1
./scripts/Test-Sessions.ps1
./scripts/Test-Admin.ps1
./scripts/Test-TicketPurchases.ps1
```

- При отсутствии восстановленных пакетов сначала выполнить restore/build без `--no-restore`. EF-команды используют локальный инструмент из `.config/dotnet-tools.json`.
- Интеграционные скрипты требуют работающих сайта и Docker PostgreSQL. Выбирать проверки по затронутому поведению; весь набор нужен для общей регрессии или финального прогона.
- Изменения интерфейса проверять через путь пользователя в браузере: видимые кнопки, ошибки формы, пустые результаты, переходы и консоль. Успешный HTTP-ответ сам по себе не подтверждает удобство сценария.
- Проверочные записи создавать с уникальными ключами и удалять только свои записи в `finally`. Не использовать реальные аккаунты для тестирования.
- Собственные процессы сайта обязательно останавливать после проверки в `finally`. Перед остановкой проверить PID и путь; не завершать чужие процессы. Не оставлять `bin/Debug` запущенным и блокирующим сборку Rider, если пользователь не попросил оставить сайт.

## БД и файлы

- Перед изменением существующих данных или применением новой миграции создавать приватную резервную копию в `backups/`. Проверять миграцию на существующей схеме и отдельной пустой тестовой БД, если она изменяет схему.
- Не удалять существующую БД или Docker volume ради исправления запуска. Не применять `docker compose down -v` к рабочим данным без прямого запроса.
- Сидирование не создаёт дубли, не удаляет пользователей/заказы и не меняет уже проданные сеансы. Время сеансов — московское, `CinemaTime`, `timestamp without time zone`; сервер и браузер не должны сдвигать его.
- Цена заказа рассчитывается на сервере. Защита от двойной покупки и повтора запроса должна сохраняться на уровне PostgreSQL и транзакции; доступ к билету проверяется по владельцу.
- Перед удалением изображений проверять ссылки в исходниках и полях БД, включая скрытые записи. Файлы постеров включать в воспроизводимые демоданные.
- Соблюдать `.editorconfig` и `.gitattributes`; не форматировать сторонние библиотеки. `libman.json` содержит выбранные готовые ресурсы, шрифты и карты; сохранять лицензии. Не загружать библиотеки целиком ради одного файла.

## Скиллы и независимая проверка

- `onlinecinema-delivery`: завершение исправления, проверки, локальный бэклог, commit/push.
- `onlinecinema-database`: миграции, PostgreSQL и демоданные.
- `onlinecinema-user-flows`: проверка пользовательских сценариев в браузере.
- Эти скиллы установлены локально в личной папке Codex; новый checkout на другом компьютере не устанавливает их автоматически. Общие правила и команды остаются в этом файле.
- Проектный субагент `onlinecinema-reviewer` описан в `.codex/agents/onlinecinema-reviewer.toml`. Использовать по прямой просьбе пользователя; также поручать ему независимую проверку перед коммитом блоков авторизации, покупки или миграций. Для небольших правок текста/стилей отдельный агент не обязателен.
- Проверяющий читает diff и код, сообщает конкретные проблемы и непроверенные риски. Он не изменяет файлы, БД, Git или настройки. Исправления и проверки выполняет основной агент.
- Если окружение не умеет выбирать именованного агента, при разрешённой делегации передать его инструкции обычному субагенту; явно сообщить об этом. Не утверждать, что профиль загружен, если это не проверено.
