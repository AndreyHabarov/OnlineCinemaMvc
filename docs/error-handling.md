# Обработка общих ошибок

В окружениях кроме Development `UseExceptionHandler` повторно выполняет аварийный запрос через `/Home/Error`. Обработчик принимает любой HTTP-метод и доступен гостю. Исключение CSRF относится только к странице ошибки; она не меняет данные.

`ErrorController` не использует PostgreSQL или AutoMapper. Страница имеет собственные стили и не подключает общий layout, поэтому доступна при сбое каталога или БД. Ответ имеет HTTP 500 и `Cache-Control: no-store`. Несуществующие маршруты продолжают возвращать 404.

Пользователь получает русское сообщение и код обращения. Перед повторной покупкой страница предлагает проверить личный кабинет: исключение не доказывает, что заказ не сохранился.

Обработчик пишет событие уровня Error с типом исключения и идентификатором запроса. Он не пишет сообщение исключения, исходный URL, query string, тело запроса, cookie или пароль. Стандартное подробное логирование категории `Microsoft.AspNetCore.Diagnostics.ExceptionHandlerMiddleware` отключено вне Development, чтобы не дублировать исключение целиком. Это правило касается общего обработчика; другие категории приложения и EF Core имеют собственные настройки журналирования. Подробный стек для разработки остаётся доступен в Development, которое нельзя использовать для публичной демонстрации.

Подход основан на [документации ASP.NET Core по обработке ошибок](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling?view=aspnetcore-8.0).

## Проверка

Из корня репозитория в PowerShell 7:

```powershell
dotnet build OnlineCinemaMvc.sln
./scripts/Test-ErrorHandling.ps1
```

Скрипт запускает отдельный процесс сайта в Production на свободном локальном порту. Вместо рабочего подключения используется тестовое подключение к сокету без PostgreSQL для воспроизведения ошибки. Проверяются реальный отказ БД, GET/POST обработчика, HTTP 500, отсутствие кэширования и технических подробностей, связь кода обращения с журналом, HTTP 404 и доступность CSS. Рабочая БД не изменяется. Процесс и сокет закрываются в `finally`; приватные журналы остаются в игнорируемой папке `backups/`.

Windows EventLog отключён только для проверочного процесса: запись в системный журнал может быть недоступна в ограниченном окружении. Консольное логирование сохраняется.
